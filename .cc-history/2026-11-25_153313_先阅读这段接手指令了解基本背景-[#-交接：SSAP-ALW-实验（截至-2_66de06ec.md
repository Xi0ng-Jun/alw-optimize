我的看法是：「通用 agent → 领域适配的基础 agent」不该是一个独立的人工步骤。它应该拆成两部分：一部分是每个场景必须由外部给的「测量定义」，另一部分是可以当作循环第 0 轮、由内部 agent 在同样的闸门下完成的「领域适配」。

## 现在的 H_base 混了两种东西

- **安全壳**：草稿区与交卷区隔离、只进不退、原子替换、警戒线、交接单、终局抢修、故障分账。对应 `src/ssap/kernel/`，约 1200 行，不含领域知识。
- **领域检查器**：本地判断「这版比上版好」的那些检查。对应 `src/ssap/checkers/alw/`，约 2600 行，全是领域知识，目前是人写的。

安全壳换场景只需要接线。领域检查器才是真正的适配，而它在方法里本来就是「第 1 类改动」，有现成的验货方式（在检验库上核对与考官的一致率）。所以它没有必须由人写的理由，人写只是热启动。

## 问题一：适配动作是否每个场景必做

必做的不是适配，而是先裸跑一遍 dev 并做失败分诊，适配做多少由分诊结果决定：

- 失败大多是「超纲」：换什么 harness 都救不了，应当停下。
- 任务短、没有强杀：安全壳本身就没收益，不用装。
- 失败集中在「本地能查但没修好」或「没交出有效文件」：才值得做领域检查器。

适配本身可以有三档参与度：

| 档位 | 外部做什么 | 适用条件 |
|---|---|---|
| 只接线 | 填事实配置，检查器全由内部 agent 从零长出来 | 单题便宜、dev 题多、裸跑已有一定通过率 |
| 接线 + 探路 | 内部 agent 先读容器里的公开文档写第一批检查器，过同样的一致率闸门 | 容器里有可用的自检工具，考官调用便宜 |
| 人写底座 | 人直接写检查器（ALW 现在的做法） | 单题极贵、每轮十几小时，从零演化烧不起 |

选哪一档主要取决于两个量：一轮实测多贵，以及检验库里凑不凑得出好坏样本。后者是硬约束：裸跑几乎没有合格品时，一致率无从核对，要么有官方参考答案，要么得有人懂怎么造样本。

## 问题二：外部与内部的边界

我建议用一条判据：**定义测量的东西必须外部给，能被测量的东西都可以内部演化。** 具体说，满足下面任一条就必须留在外部：

1. 它定义了分数或防泄漏边界，循环无法用自己的证据验证它。
2. 它需要内部 agent 被禁止看到的信息（考官源码、参考答案、val/test）。
3. 它是安全、权限或预算上限。

按这条判据，外部研究员每个新场景要交付的是：

- **任务契约**：工作目录、交卷文件、时限、哪些文件不可改。
- **考官接口**：怎么调用、怎么读出总分和分项、重复打分是否稳定、对 agent 隔离。
- **题目切分**：哪些题属于同一底层项目，dev/val/test 怎么分。这需要领域判断，也不能交给有动机刷分的一方。
- **故障分账规则**：哪些退出算设备故障（各领域工具有自己的崩溃方式）。
- **改动许可面与预算**：harness 允许改哪些位置、最多几轮、并发多少。
- **agent 栈接线**：安全壳怎么挂到具体的命令行外壳上（hook、入口脚本）。这一项按 agent 栈做一次，不按任务领域做。

其余都可以内部演化：检查器、经验探针、报错翻译器、提示词和策略、抢修流程。

## 两个需要你拍板的点

- **「内部」的定义要包含模型约束。** 内部指：用同一个固定模型、只看 dev 证据、过同样的闸门。如果探路阶段用了更强的模型（或者由我来写），它在归因上就是外部贡献，和人写没有区别，「模型不动」的说法也会被削弱。
- **归因要多切一段。** 如果把领域适配移进循环，对比表应变成：裸跑 → 只装安全壳 → 适配后底座 → H*。这样人的贡献只剩可核对的事实配置，人写的底座可以留作对照臂，回答「自动适配追上人工适配多少」。

这套划分目前是我的判断，仓库里唯一的实例是人写底座那一档，「只接线」和「探路」两档都没有实验支撑。

## A：代码仓库修 bug

1. **外部交付**
   - 契约：在仓库目录干活，交一个补丁，测试文件不可改。
   - 考官：应用补丁后跑隐藏测试，返回过/不过。
   - 切分：按仓库分簇。
   - 故障规则：依赖下载失败、构建超时算设备故障。
2. **裸跑分诊**：预期三类都有：补丁为空或应用不上、把原有测试改坏、公开测试全过但隐藏测试挂。
3. **为什么只接线**：单题便宜、题多、裸跑就有相当数量的通过样本，检验库天然有好坏两类补丁，检查器可以从零长出来并核对一致率。
4. **内部会长出什么**
   - 有覆盖权的检查：补丁能否干净应用、原有测试是否仍通过（都对应考官的公开步骤）。
   - 只当参谋的探针：为问题描述写一个复现测试。
   - 报错翻译：压缩测试失败日志。
5. **特点**：每轮可以全量重跑 dev，不需要「只重跑最后一段」的省钱评估。主要丢分预计在隐藏测试，那是信息缺口，探针没有覆盖权，收益上限不确定。

## B：流体仿真算例搭建

1. **外部交付**：除契约和考官接口外，有两件事需要领域判断。
   - 切分：同一几何、不同流速的题算同一簇。
   - 稳定性：同一份交卷重复打分是否一致（并行求解可能有差异），要先实测。
2. **裸跑分诊**：预期大多是算例跑不起来或发散，几乎没有合格品。
3. **为什么不能只接线**：检验库没有好样本，一致率无从核对。需要把官方参考算例锁进隔离的检验库，再对它造坏样本（改坏网格、改错边界条件），由考官打真标签。造法可以由内部 agent 提，参考算例本身不能给它看。
4. **内部会长出什么**：网格质量、残差收敛、守恒这三类有覆盖权的检查；求解器日志翻译（哪一步哪个物理量开始发散）。
5. **特点**：每轮十几小时，总轮数很少，探路阶段第一批检查器的质量决定大半结果。这类场景保留人写底座做对照臂最有意义。

## C：机器学习竞赛

1. **外部交付**：契约（交一份预测文件）、考官（隐藏测试集上的指标分）、合格线（基线分或奖牌线）、切分（同一数据来源的竞赛算同簇）。
2. **裸跑分诊**：预期大多能交出文件，丢分在「本地验证分高、考官分低」。这里「本地能查但没修好」和「挂在隐藏项」两个篮子分不清。
3. **关键差别**：本地验证分是有噪声的估计，不是考官步骤的镜像。
   - 文件格式检查（行数、列名、无缺失值）可以拿覆盖权。
   - 本地验证分只能当参谋，不能用来替换交卷区的版本，否则会把过拟合的版本推上去。
4. **内部会长出什么**：主要是时间分配和验证方式这类策略改动，比如「留一份从不参与调参的数据做最后选择」。这类改动离线验不了，只能靠实测，每轮只能试一两个。
5. **特点**：安全壳的收益只剩「到点保证有一份合法提交」。方法里靠镜像认证筛改动的那部分，在这里只覆盖格式层。

## D：短问答 / 表格分析

1. **外部交付**：只剩考官接口和切分。
2. **裸跑分诊**：没有强杀、没有中间草稿、没有本地可查项，四个篮子塌成「对/错」。
3. **流程**：改提示词或工具，全量重跑 dev，比分数。安全壳、检验库、终局抢修都不装。
4. **特点**：能沿用的只有纪律（按簇切分、val 只用一次、test 只开一次、分段归因）。优化本身用现成的提示词搜索方法就够了。

- **定不了的**：需要有权的人拍板。例二就是这种，它会问：「客户端正常退出触发的网关错误标记，算设备故障还是有效运行？」

它自己跑一下就能查清的事不该问。比如网关上模型的完整名字，查一次模型列表接口就知道。

## 「黑箱不关心谁回答」是什么意思

回答进了材料夹之后，和研究员一开始放进去的文档没有区别，都只是一段文字材料。所以回答的可以是研究员，也可以是研究员拿着问题去问更强的模型，或者去翻考官源码后转述。黑箱的流程不变。

## 没有这个通道会怎样

agent 遇到缺口时只能自己猜，而且猜的结果会无声地写进代码。例一如果猜错，它会把「DRC 得分为 0」理解成 DRC 检查器有问题，然后去改一个本来没错的检查器。

另外两点：

- **不阻塞**：外部一时答不上，agent 按一个明确标注为「暂定」的假设继续，之后有了回答再修正。
- **不是求助做题**：问题只能关于场景的事实和规则，不能问某道题怎么做。回答同样受那条红线约束：答的人不能看过 val、test 的结果。

这个机制目前只是设计，代码里还没有：现在的提案格式只有改动本身，没有提问的字段。

## Assistant <sup>11/25/2026, 5:48:20 PM</sup>

四个 agent 都回来了。下面是综合后的设计说明；凡是四份意见有分歧的地方，我做了取舍并在后面标明。

## 一句话

方法只管沙盒外面的几件事（考试、打分、记录、预算、交付），沙盒里面放一个像工程师一样干活的 agent。材料随便给，它自己读、跑、看、改、问，直到预算用完，交出一个适配好的 harness 文件夹。

## 怎么运转

1. 研究员交三样东西：
   - 一条能跑一道练习题并拿回官方分数的命令；
   - 一个材料文件夹，格式不限；
   - 预算和权限。
2. 开发 agent 拿到材料、练习题和两条命令：
   - 「用某版 harness 跑某题」：贵。
   - 「对一份已存档的结果重新打分」：几分钟，不花模型费。
3. 它自己决定读什么、跑哪题、改什么。可以改 harness 里的任何东西：说明文字、做法文件、工具脚本、自动检查、时间安排。
4. 材料里找不到或自己定不了的事，写进一个提问文件，同时注明「不答我就按某假设继续」。外部的回答作为新材料加进文件夹。
5. 预算用完，它交出一个文件夹和一条启动命令。
6. 外部在全新环境里先跑通一道练习题，然后在密封的最终考试上考一次。

## 方法固定的只有六条，全在沙盒外

1. **题目隔离**：练习题和最终考试题按来源分开，名单最先锁定。最终考试的题和答案不进沙盒、不进材料，沙盒不联外网。
2. **打分不可改**：只用官方打分程序，在沙盒外执行，原始结果原样返回。
3. **全部留痕**：每次运行都记录版本、题目、原始分和花费，失败和中断的也记，不能删。
4. **预算和做题模型由外部强制**。
5. **材料和问答只增不改**，全部存档。回答的人不能看过最终考试的题和结果。
6. **交付即冻结**：最终考试只考一次、多个种子，与基线同场对比，报真实花费。

对比报三行：原始 agent → 把材料直接给做题 agent → 本系统的产出。中间那行是为了回答「功劳是不是只来自材料本身」。

## 其余全部留给 agent

领域检查、报错整理、提示词、时间警戒线、保底备份、收尾抢修、怎么诊断丢分、要不要自己留几道练习题不看。

现在已有的通用安全代码和这次项目的踩坑经验，都变成材料文件夹里的参考资料，不再是规定。

## 相比现在的方法去掉什么

- 人先写底座这一步。
- 改动分四类、各有权限和离线筛查流程。
- 每轮只改一处、两轮无效就删除。
- 失败分四类的固定诊断。
- 禁止「提示词教程」的规则和禁词表。
- 练习题内部再遮住四分之一。

最后两条直接挡新方向的路。一位 agent 指出：现在所有高于 0.1 分的运行都在被遮住的那部分里，提案方看到的 16 次运行没有一个成功样例。

## 分歧和我的取舍

- **要不要把「先核对打分是否可靠」定为固定步骤。** 两位主张固定，一位主张留给 agent。我选择先不固定，只写进给 agent 的初始工作习惯里，然后用下面的验证看它会不会自己做。不会，再升为固定步骤。
- **要不要规定「从小到大逐级放大」和「一次只改一处」。** 我选择不规定。每题 3 小时的场景里一次改一处根本测不过来。

## 需要你定的三件事

1. **AGENTS.md 的不变式 1**（只进不退的交卷更新、禁止中途强制回滚、只有与考官一致的检查才能覆盖）在新设计里从规则降为参考资料。这违反现行约定，要你同意并改 `docs/mcr-formal.tex` 才能做。
2. **开发 agent 用什么模型。** 四份设计都默认它是强的编码 agent。服务器上现在能用的是做题同款模型，这是最大的不确定点。

## harness 文件夹和「直接修改 harness 本身」

你的理解是对的，是我原来的措辞太窄，已经改了。文件夹只是交付物的外形，不限制改到多深。

改 harness 有两种深度：

- **通过产品提供的方式改。** 不动 agent 产品自身的程序，只往上加东西：说明文件、做法文件、自定义工具、在特定时机自动执行的脚本、配置项，或者在产品外面包一层程序管时间和收尾。
- **改产品自身的程序。** 直接改它的源码，能改到前一种够不着的地方：怎样管理上下文、怎样截断工具输出、怎样组织多步操作。

哪一种可行取决于产品本身：

- Claude Code 的源码不公开，只能用第一种。ssap 现在的保底壳全部属于第一种：安装原样的 Claude Code，外面包一层入口脚本，再用它提供的扩展方式挂上检查。
- pi 是开源的，两种都可以。

新的写法是：文件夹装的是「启动做题 agent 所需的、除模型和题目环境之外的全部东西」，起点是通用 agent 原样的样子。用第二种时，文件夹里直接放一份改过的产品，启动命令调用这一份。方法对两种一视同仁，都只是文件夹的一个版本（文档第 8.1 节）。

我的建议是默认从第一种做起，理由有三条：

- 领域适配的主要内容（领域知识、检查、工具、时间安排）第一种都装得下。
- 改动容易读懂，产品升级时不容易坏。
- 改源码的搜索范围大得多，更容易把原本好用的东西改坏。

只有当瓶颈明确出在产品自身的行为上时，才值得用第二种。这是判断，没有实验对比过两种方式。
